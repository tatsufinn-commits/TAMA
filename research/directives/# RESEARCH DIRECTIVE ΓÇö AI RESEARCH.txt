# CRITICAL RESEARCH PRINCIPLE — STUDY THE SCAFFOLDING, NOT PRIVATE IMPLEMENTATIONS

The objective is to understand **how systems with these capabilities can be constructed**, not to pretend that private or proprietary implementations are publicly known.

For proprietary systems such as NotebookLM, ChatGPT, Gemini, Claude, Perplexity, or similar platforms:

**DO NOT claim knowledge of private source code, internal architecture, proprietary algorithms, private infrastructure, hidden prompts, or undocumented implementation details unless credible public evidence explicitly establishes them.**

Instead, investigate what can legitimately be learned from:

* official documentation
* public technical publications
* academic papers
* patents where relevant
* official engineering blogs
* developer documentation
* public talks and presentations
* public interviews with engineers
* observable product behavior
* public APIs
* open-source components
* open-source projects attempting similar functionality
* public benchmarks
* technical discussions
* credible third-party analysis

The goal is to reconstruct the **general engineering principles and architectural patterns** behind these capabilities, not to fabricate a reconstruction of proprietary internals.

# EVIDENCE CLASSIFICATION

Every significant architectural claim should be classified according to the strength and nature of the evidence.

Use the following categories:

### DOCUMENTED

Explicitly stated by the system's creators or official documentation.

### OBSERVED

Demonstrated through publicly observable behavior or reproducible testing.

### IMPLEMENTED

Demonstrated through publicly available source code or an open-source implementation.

### RESEARCH-SUPPORTED

Supported by academic or technical research.

### INFERRED

A reasonable technical inference based on observable evidence.

### SPECULATIVE

A hypothesis that cannot currently be established.

Never present **INFERRED** or **SPECULATIVE** information as confirmed architecture.

When discussing a proprietary system, explicitly state which category applies.

For example:

> **Claim:** The system likely uses retrieval to ground responses in uploaded documents.
> **Evidence:** OBSERVED + RESEARCH-SUPPORTED
> **Confidence:** High
> **Private implementation:** Unknown

# PUBLIC-EVIDENCE RECONSTRUCTION

When studying a proprietary system, create a section called:

## PUBLICLY ESTABLISHED ARCHITECTURE

Document only what credible public evidence supports.

Then create:

## PLAUSIBLE TECHNICAL INTERPRETATION

Explain how the observed capability could reasonably be implemented using known technologies and research.

Then create:

## UNKNOWN / UNVERIFIED

Explicitly identify what cannot currently be established.

This three-layer structure is mandatory for proprietary systems.

Example:

```text
NotebookLM

PUBLICLY ESTABLISHED:
- Accepts user-provided sources.
- Generates source-grounded responses.
- Provides citations/references.
- Supports document-based interaction.

PLAUSIBLE TECHNICAL INTERPRETATION:
- Retrieval-based context selection is likely involved.
- Document indexing is likely involved.
- Some form of source-aware generation is likely involved.

UNKNOWN:
- Exact retrieval architecture.
- Exact embedding model.
- Exact chunking algorithm.
- Internal orchestration.
- Private infrastructure.
- Internal ranking mechanisms.
```

Do not collapse these three categories into one.

# AVOID ARCHITECTURAL CARGO CULTING

Do not recommend a technology simply because a famous AI product appears to use it.

For every major recommendation ask:

> **What problem does this solve?**

> **Is there evidence it solves that problem effectively?**

> **What is the complexity cost?**

> **Could a simpler architecture accomplish the same thing?**

> **What happens when the system scales?**

> **What happens when it fails?**

Avoid recommendations such as:

> "Use a vector database because NotebookLM probably uses one."

Instead:

> "A vector database may be appropriate because the system requires semantic retrieval across a large document collection. Evidence X and implementation Y demonstrate this pattern. However, for a small corpus, simpler retrieval may be sufficient."

The goal of this research is **NOT** to immediately build a clone of NotebookLM or reverse-engineer proprietary software.

The research should allow a future development agent to answer:

> What already exists?

> How does it work?

> What is only inferred?

> Why does it work?

> What doesn't work?

> Which architectural patterns are proven?

> Which are experimental?

> Which ideas should we borrow?

> Which should we avoid?

> What are the tradeoffs?

> What research still needs to be done?

> What architecture is justified by the evidence?
